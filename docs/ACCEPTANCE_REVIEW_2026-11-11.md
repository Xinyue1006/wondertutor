## Client decisions and integration release gates

These are not cosmetic tasks and must not be hidden by a green unit-test count.

1. **Complete the other side of the journey.** Current `App.jsx` still uses placeholders for Tutor Dashboard, Booking Requests, My Students and Earnings, plus Admin Booking Oversight, Financial Management and System Configuration. A real parent cannot rely on an unbuilt tutor acceptance/attendance/summary/refund administration journey. Integrate teammate work in staging before client handover.
2. **Gateway/merchant readiness.** The client needs an eligible merchant account and approved payment configuration. Keep simulation clearly in development; verify signed callback retry/idempotency and original bill after checkout timeout against the real sandbox before taking money.
3. **Refund execution and arbitration.** Client-approved eligibility, decision authority, partial-refund percentage/process, settlement evidence and disputed/no-show handling are still needed. Do not label an approved request “paid back.”
4. **Suspension policy.** Decide account-wide lockout versus read-only history versus function-specific suspension. Current global deactivation differs from Form2; existing lesson/payment obligations must have an operational owner.
5. **Hosting and operations.** Hostinger subscription/hPanel, HTTPS/domain, DB TLS/access/backups, restore drill, cron ownership, storage permissions, log retention and monitoring need actual staging evidence. `docs/HOSTINGER_DEPLOYMENT.txt` is a proposal/runbook, not proof of deployment. No host account was inspected by this workstream.
6. **Privacy and child data.** Child data is accessed by role/ownership and private evidence files use signed delivery, but the interview's per-field “hide sensitive child information” control is not represented in the current Child schema. Confirm the intended visibility model. Avoid collecting medical/learning-disability information in free text until access/retention is agreed. Formal legal/privacy compliance is not certified here.
7. **AI expectations.** Approved matching weights are deterministic; Gemini interprets read-only requests. Free-tier timing is variable and does not guarantee Chapter3's five-second chatbot target. Run a separate frozen, held-out multilingual evaluation rather than reusing prompt-tuning diagnostics as the final score.
8. **Human acceptance.** Observe at least one first-time parent, tutor and administrator completing realistic scenarios without coaching. Record task completion, time, errors, help requests and short satisfaction feedback. Code inspection and automated browser checks cannot establish client satisfaction on their own.

## Report corrections needed before submission

- Chapter4 currently says **23 tables**; current Prisma has **25 models** (moderation adds fields/relations, not another portal/database). Use `CURRENT_DATA_MODEL.md` and the final schema as the source of truth.
- A role is an application rule: the schema does not enforce “every User has exactly one ParentProfile or TutorProfile.” Admin has neither; both optional one-to-one relations exist at DB level.
- Chapter4's old statements that password changes leave tokens valid and qualification files are ordinary public links are out of date: credential tags and private media delivery were added. Describe the implemented controls and their residual risks accurately.
- Trial lessons were removed by the user's later decision; `Booking.isTrial` remains a legacy storage field and new requests reject `true`. Older “paid trial” diagrams/text should be revised.
- Hostinger is the current deployment direction. Older CLAUDE/draft references to Vercel/Render are historical and must not be presented as actual infrastructure.
- Guided matching persists a `MatchingRequest`; read-only LLM searches are deliberately temporary and not saved. `MatchingRequest.childId` is currently a scalar, not a declared foreign-key relation.
- Multiple selected dates create multiple one-hour Booking rows in one atomic request, not a recurring subscription and not a new BookingBatch table.
- A domain class diagram describes entities and service dependencies. The JavaScript implementation does not contain a PHP/Laravel-style class for every controller or an explicit `models/` directory; Prisma schema/client provide the persistence model.

## UI reliability and privacy-copy fixes from this workstream

- Progress-report responses are now applied only if they belong to the latest request. Older filter responses cannot overwrite the newest report. CSV/print actions are disabled while updating, after an invalid period or after a failed refresh, and failed updates have a retry action.
- Child-progress pages do not display the previous child's records while a new child route loads or fails. Obsolete responses are ignored.
- The notification bell shows loading and recoverable errors. A failed notification fetch no longer displays a misleading empty-inbox message. Failed mark-read/mark-all actions are reported instead of silently ignored, and simultaneous action clicks are guarded.
- The account-deletion explanation now distinguishes removed profile fields from retained lesson/payment/case records and warns that names in retained free text or evidence may remain. This is accurate disclosure, not a claim that a complete retention/anonymization workflow was implemented.

Focused frontend regressions: **19 passed** across `ProgressReport.test.jsx`, `ProgressNavigation.test.jsx`, `NotificationBell.test.jsx` and `PrivacyAccountCard.test.jsx`. These checks cover racing responses, child-route isolation, export blocking/retry, notification network failure and retention disclosure. No database test or production query was run by this workstream. The main review owns overall runtime and browser results.
